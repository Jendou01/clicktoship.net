# Controlled release runbook

Remote deployment is not implemented or authorized. `release-readiness.yml` is workflow_dispatch-only packaging, no SSH/domain/registry secret/deploy step. Its environment `staging-readiness` must have required human reviewers configured by repository owner; YAML cannot enforce that setting itself. It verifies exact40-character SHA is on main and hosted Foundation CI succeeded, checks tracked artifacts, builds images and uploads seven-day image/checksum/SHA/ID artifacts. It does not claim signed provenance or application-host security approval. Inspect workflow and build tools from the exact reviewed commit before triggering; package creation never authorizes deployment.

After exact host and change window are separately authorized:

1. Freeze a reviewed release record: owner/host/domain/region, Git SHA, immutable image refs, CI URL, independent approval, migration inventory/compatibility, expected schema, prior image refs, secret versions (not values), rollback point, evidence IDs and operator/time. Protect the record against edits.
2. Run SECURITY_PREFLIGHT, backup freshness/restore/keys/storage checks. A failed/unavailable check aborts before ingress or migration. Maintenance/migration privileges are one-shot and never inherited by runtime.
3. Quiesce ingress/writers/worker queues and singleton scheduler under the maintenance plan; do not lose unknown carrier work, leases or reservations. Take a consistent encrypted DB/object snapshot and verify local hashes, authenticated decryption/catalog and actual offsite upload receipt. Record backup SHA/point and key-escrow identity separately.
4. Inventory `migrate:status` and release migration files. Inspect SQL offline; Laravel `migrate --pretend` is not a sandbox for arbitrary migration PHP/side effects. Test the exact upgrade on a restored disposable copy first. Preserve irreversibility/append-only evidence.
5. Explicit maintenance profile migrates forward with `migrate --force --no-interaction`; apply reviewed `runtime-grants.sql` and privilege tests after every schema change. Do not grant future default DML to unknown tables. No migrate:fresh/db:wipe/down-v/truncate against retained data.
6. Start exact reviewed API/web/gateway images, run schema/config/health/TLS/auth/gate/locale checks before reopening ingress. Start one scheduler and two isolated Horizon roles; compare actual process/queue assignments and monitor receipt recovery. Use current session/MFA checks for operator workflows.
7. Record successful health, backup/migration/schema/image IDs and operator approval before opening protected staging to synthetic reviewers. Watch thresholds and reversible app behavior. Failure enters ROLLBACK_RUNBOOK; never fix a failed release by disabling gates or replaying ambiguous operations.

Do not run schema migration automatically on every API/container restart. Do not cache a shared config file across Horizon roles; their tmpfs caches are separate. Changing a tag or restarting an old container is not proof it is running the intended digest.

Packaging exports local content IDs, not registry manifest digests. Before actual hosting, select an owner-approved registry/promotion policy, promote the protected reviewed images and resolve their immutable manifest digests for CTS_*_IMAGE/preflight. No registry credential or push is configured here. A direct archive-only promotion would need a separately reviewed provenance/ID validation procedure; the simulation-only image-ID flag cannot certify a remote release. This unresolved promotion choice remains part of B16-02/B16-10.
