# Phase 8 — private bulk shipment preparation

Base: main, PR #7 merge `6921d5c0a34cf5a5e05ae949939cd5f8ac34592b`. Bulk is a module in the existing monolith, never a second shipping/pricing/financial implementation. No live carrier, payment, pickup or label activation and no Phase 9 work.

## Boundaries and lifecycle

The module owns batches, encrypted file metadata/source rows, mapping revisions, validation history, duplicate decisions, public pricing previews, approvals, draft references, commands, work intents and audit events. `initialized → parsing → mapping → validating → review → pricing → review → preparing → completed/partial`. Invalid files fail safely. Revoked authority blocks work. Failed/blocked history is retained; cancellation is permitted only before any shipment draft commits. Cancelled/completed/partial batches do not reopen.

Upload initialization is idempotent; upload content is checksum-bound and immutable. The file remains private. Security inspection and parsing run in the background before source rows can be read. Mapping is explicit (suggestions are not silently accepted), versioned and immutable. Every remap creates new validation history and invalidates previous preview applicability. Mapping cannot change after approval. Rows contain one shipment each, with optional JSON package/customs arrays for multiple packages/items.

`ShipmentInput::draft/report` and the shared Shipping `DraftReadiness` application service are the validation authority. The shared service additionally checks that a service is a current published global service through Pricing-owned discovery, so an unknown/disabled service is not labelled locally ready in either single or bulk workflows. This does not enable a carrier or accept a quote. No competing shipping validation rules or alternative currency/COD policy. SAR is the currently supported currency. Integers represent minor units, grams and millimetres; numeric scientific/decimal money is not silently converted. Arabic-Indic digits normalize in flat numeric/phone fields, Unicode text normalizes to NFC, and existing shipping city normalization is reused. Required country-specific postal/state and international manufacturing/customs data comes from the Phase 7 readiness report.

Phase 5 `Calculator`, catalog and configured carrier-cost source calculate informational public estimates through a Pricing-owned `ImportEstimates` application boundary. Public snapshots are allowlisted; contract costs, selected confidential configuration and margins never leave Pricing. Missing approved configuration is explicitly unpriced. Totals use bcmath integer strings, partition by currency and include priced rows only. Expired snapshots are labelled; they are never automatically accepted by a shipment. A fresh Phase 7 quote, revision/expiry validation and existing gates remain required before any later submission.

Preparation uses the Shipping-owned `Shipments::importDraft`, with the same draft persistence/event implementation as the existing single-shipment HTTP service. It rechecks captured authority, uses a permanent per-batch/per-row business key and creates a draft only. A draft/reference/event/cursor transaction commits together. No wallet, hold, quote acceptance, submission, carrier operation, pickup, label or payment call exists in this module.

## Duplicate policy

Duplicate detection is separate from command idempotency. File SHA-256 matches are scoped to the same merchant and flag a prior upload; they never silently suppress a new batch or copy approvals. Canonical shipment hashes are tenant-specific HMACs over normalized complete shipment content plus an optional merchant reference. Matching recipient details alone do not imply a duplicate. Within-file, within-batch and earlier-batch matches require an explicit, immutable keep-as-separate or skip decision. Every flagged row must be resolved before approval. Keeping two identical shipments deliberately yields two separate drafts, each with a distinct row business identity.

Command keys are scoped by merchant, actor and operation, bind a canonical payload digest and reject changed payloads with HTTP409. Row numbers/IDs, mapping versions, immutable validations and unique draft references survive retries. Replay cannot bypass current membership/token permissions. Decisions cannot be edited in place; remapping restarts review, and approved imports cannot be remapped.

## PostgreSQL, jobs and recovery

The transaction order is Pricing catalog shared lock (when processing), merchant root, work/batch state and user/credential rows, consistent with the existing modules. Commands use the existing ShippingAccess lock/revalidation boundary. Workers recheck merchant/account/membership status, built-in permissions, token scope/version/revocation/expiry or session registry validity before each committed row/chunk. Pricing additionally needs rates.quote; preparation additionally needs shipments.write. No raw session cookie/token secret is stored: only provenance registry IDs and authentication version.

`bulk_work` is the transactional durable work/outbox record, not Redis. One active work item per batch; work IDs bind phase/mapping revision. Encrypted queue notifications contain identifiers only. A 90-second lease prevents overlapping workers; cursor and effects commit together. Crashes before commit roll back; lost responses and redelivery reuse permanent row keys. Completed/stale work IDs cannot drive a newer phase. `bulk:recover` republishes up to 100 unleased/expired intents each minute, even after Redis job loss. Five interrupted-lease recovery attempts are allowed per work item; repeated failures become a retained failed batch rather than an infinite retry loop. Normal chunk continuation does not consume this recovery budget.

Parsing streams from a verified decrypted scratch file into encrypted PostgreSQL rows in bounded chunks. Retrying parsing reads the immutable source again, verifies raw hashes and reuses source-row identities; no duplicate insert. Validation/pricing/preparation resume via cursor. Parsing restarts are bounded by file/row/time limits; validation/preparation never require the complete file in PHP memory. Partial success preserves already-created drafts. After the first draft commits, cancellation returns409 rather than deleting drafts or pretending to undo work. Blocked authorization is not silently reassigned to another actor; a new authorized import/review is required.

## Storage and spreadsheet security

Original bytes use sodium authenticated secret-stream encryption in the private local disk with server-generated UUID keys. Filename and source/draft payloads are encrypted. Bounded 64KiB frames include an authenticated final marker; size/checksum are verified before parsing. A private 0600 scratch file is removed in finally. No original-file download, arbitrary path/URL input, public symlink, raw payload logging or Redis source-row payload.

CSV is strict UTF-8, optional UTF-8 BOM, comma/semicolon/tab dialect (API uses `tab`), RFC-style quoting and embedded quoted line breaks. Record and cell limits are enforced while reading, before unbounded record accumulation. XLS/XLSM/password-encrypted archives are rejected. XLSX is a restricted single worksheet stored at xl/worksheets/sheet1.xml, with inline/numeric/shared strings. Only a small OOXML part allowlist is supported; macros, extra sheets, embedded objects, external relationships, formulas, hyperlinks, XML DTD/entities, symbolic entries, duplicate names, traversal, corrupt references and expansion bombs are rejected. Unsupported workbooks must be exported as a simple single-sheet workbook or UTF-8 CSV; no hidden sheet is silently dropped. No formulas/macros/links/styles are evaluated.

This is actual structural security inspection, **not an antivirus certification**. Production processing fails closed (`MALWARE_SCANNER_REQUIRED`) until an approved malware scanner and storage/retention/deployment policy are installed. Local/testing structural inspection is explicitly limited to development. No production enable flag is supplied by HTTP. The private local disk is a development adapter; shared worker storage, encryption key rotation, malware service, retention/deletion/privacy policy, disk quotas/monitoring and least-privilege DB/runtime principals remain launch decisions.

Limits in config/bulk.php: 10MiB upload, 10,000 data rows, 96 columns, 4,096 bytes/cell, 256KiB CSV record, 32MiB archive expansion, 64 archive entries, ratio100, 100,000 shared strings, 100 rows/chunk, 40s parser budget, 60s job timeout, five pending batches, 20 initializations/rolling24h and 100MiB retained original bytes per merchant. HTTP and PHP body limits are aligned to 10MiB files/12MiB multipart requests without raising other API body limits. Validation/preparation commits one row per transaction; parsing stage transactions are chunk-bounded. Infrastructure limits remain a ceiling when changing application limits.

## Read APIs and UI

All endpoints derive merchant identity from the existing authenticated context. Granular bulk.read/upload/map/price/prepare/cancel/export permissions are assigned additively to built-in operational merchant roles; Viewer gets read-only access, Finance/platform roles receive no automatic recipient-data access. No platform tenant bypass. Composite foreign keys bind merchant, batch, source row, work, mappings, validation and created shipments. Immutable-table and batch identity/state guards prevent reassignment or history rewriting.

Source inspection is paginated and authorized; original bytes are not downloaded. Error reports stream CSV with localized field labels, formula-neutralized cells, attachment/nosniff/sandbox/no-store headers and audited access. Prefixing dangerous spreadsheet cells with an apostrophe includes legitimate phone numbers beginning with +. This is an export representation; the original source remains immutable.

EN/AR routes: bulk, bulk-import, bulk-results, bulk-history. These contain dashboard/history, native upload progress, format/dialect/templates, mapping, validation and safe source disclosure, explicit duplicate decisions, estimate availability/expiry/totals, approval acknowledgement for unpriced drafts, durable progress, results and audit/error-report controls. Refreshing progress is user-controlled; no high-frequency polling or unsafe automatic command retry. Selected batch UUID survives locale switches; server tenant checks remain authoritative.
