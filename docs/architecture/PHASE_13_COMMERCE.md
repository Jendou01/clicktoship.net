# Phase 13 scope and ownership (recorded before implementation)

Base main: Phase 12 merge 35400617214e3da08d6bfef29434cc30832c13db. Feature branch feat/phase-13-salla-integration. The repository fetch refspec only updated origin/HEAD; main was explicitly fetched into origin/main and fast-forwarded after verifying its merge and Phase 12 parent.

Commerce owns durable merchant/store identity, encrypted current credentials, hashed session-bound one-use authorization intents, encrypted immutable normalized order snapshots, synchronization runs/checkpoints/leases, authenticated receipt metadata, commands, events and links to existing shipment drafts. It never writes a ledger, carrier request, tracking projection or shipment revision directly. Shipping.importDraft remains the sole draft creation boundary; readiness, current credentials and existing service validation are reused. Bulk file parsing is not reused for API orders; its bounded work/origin reauthorization/idempotency patterns are reused without creating fake import files.

Official documentation is inaccessible: see ../integrations/SALLA_EVIDENCE.md. Runtime Salla adapter and external webhook/OAuth activation remain closed. Provider-neutral internal DTOs and test-only synthetic adapter prove lifecycle behavior without inventing Salla JSON, URLs, scopes, events or fulfillment policies. Other commerce providers are not implemented in Phase 13.

Permissions: integrations.read, integrations.manage, integrations.sync, orders.read, orders.prepare. Owner/Admin receive all; Shipping Manager receives integration/order reads, sync and draft preparation; Shipping Operator receives order reads/preparation; Viewer receives reads; Finance receives no customer order data by default. Existing shipments.write is independently required for any draft; originating session/token abilities and current membership/status/auth version are rechecked for every durable work step. Platform.metrics.commerce authorizes aggregate counts only (Super Admin/Operations/Support); no new private bypass or grant capability. Private store/order access is through ordinary merchant membership only until an exact-granted provider-specific support policy is approved.

One provider/store identity is permanently bound to one merchant in this phase, even after disconnect. No browser-supplied store identity establishes ownership. Reconnection requires server-verified provider identity and a fresh session-bound authorization intent; transfer is blocked pending independently approved ownership/retention policy. Tokens encrypt at rest, never serialize/log; current refresh lease/version prevents concurrent refresh/late-response resurrection. An ambiguous rotating-token refresh requires reauthorization, not blind retry.

Sync fetches outside DB transactions, then locks merchant/current origin/connection/run before atomically committing each bounded page and checkpoint. PostgreSQL durable work survives Redis loss, leases fence stale workers, recovery republishes unfinished work, and attempt/page/row caps prevent infinite provider pagination. Checkpoints and opaque cursors are encrypted and distinct. Older/undated conflicting snapshots are retained without replacing reviewed/current data. Linked drafts are never overwritten: source change is a review flag only. No automatic carrier cancellation follows source cancellation.

Draft preparation is explicit, previewed, optimistic and idempotent, with a bounded 25-order batch, per-order committed results and current authority/generation rechecks. Merchant supplies genuinely missing origin/package/service data; recipient/amount/COD/source identity are never fabricated. COD/non-SAR/unknown payment/fulfillment eligibility remain blocked by current Shipping rules or missing official policy. A permanent order-to-draft link plus merchant locking prevents duplicates across actors, retries and crashes. Historical links remain on disconnect and cannot authorize new writes.

No live API request, public tunnel, production DNS/deployment, real shipment/paid waybill/charge/COD settlement/customer notification, automatic merge or Phase 14. Retention is review-only (counts, no hard deletion); lawful customer retention/redaction policy and secure backup/key lifecycle require approval before real order ingestion.

## Implemented data and transactions

Two additive migrations: `2026_10_25_120000_create_commerce` installs the 12 integration-owned tables; `2026_10_25_121000_fence_commerce_authorizations` adds indexed cancellation evidence to authorization intents. No old business data is backfilled or seeded. The second migration is additive because the initial migration had already been applied in the development environment; no normal database rollback/reset or hand-edited migration history was used.

| Table | Purpose and constraints |
|---|---|
| commerce_connections | Provider/store identity globally unique and permanently merchant-bound; immutable identity trigger, generation/version, current authorization provenance and originating credential reference |
| commerce_credentials | Current encrypted access/refresh pair only, expiry/scopes/version and refresh lease; cleared on disconnect/ambiguous rotation; composite merchant/connection FK |
| commerce_authorizations | Hashed one-use state, exact approved HTTPS redirect, actor/session/auth-version/merchant binding, 10-minute expiry, consumption and cancellation evidence |
| commerce_orders | Scoped external identity, blind-indexed exact reference, current snapshot pointer, status/version/review flag and source creation time; immutable identity trigger |
| commerce_snapshots | Append-only encrypted minimized internal normalized data, canonical digest and nullable source update time; composite order FK, per-order digest uniqueness |
| commerce_runs | Durable sync/preparation work, originating actor/session/token/auth version, connection generation, encrypted batch/cursor/checkpoint and bounded lease/attempt state |
| commerce_pages | Immutable per-run cursor receipts, preventing pagination cycles and duplicate page commits |
| commerce_draft_links | One permanent source-order→existing Shipping draft, immutable snapshot/review binding and scoped shipment FK; survives source changes/disconnect |
| commerce_results | Immutable per-run/per-order partial outcomes, scoped order/shipment references and safe error codes |
| commerce_commands | Actor/merchant/operation/request-key digest and replay result (identifiers only); no duplicated customer snapshot |
| commerce_events | Immutable module/audit events; allowlisted identifiers/counts/codes, no credentials or customer response bodies |
| commerce_receipts | Authenticated provider signal metadata only, scoped event identity/body digest and duplicate/collision fence; no raw webhook payload store |

Composite foreign keys prevent cross-merchant order/snapshot/run/draft/result relationships. PostgreSQL rejects UPDATE/DELETE/TRUNCATE on snapshot/page/link/result/command/event/receipt evidence. Partial unique index permits one active run of a kind per connection. Scoped directory/reference/recovery/pending-authorization indexes support the actual access paths. SchemaIntegrity checks real tables, enabled immutable/identity triggers, cancellation column and valid indexes independently of migration rows. Downgrade refuses retained normal connection/authorization history; disposable tests remove the cancellation migration before the core and verify previous phase data survives.

HTTP mutations and reads lock the existing merchant root, lock/reload the user, revalidate current session or token and resolve current membership/permissions through ShippingAccess. Client merchant/actor/origin/store identity fields are prohibited. No platform role establishes merchant context. Private responses are no-store, and list endpoints are bounded 25 UUID-keyset rows, explicitly ordered by internal UUID rather than pretending provider ordering. Exact reference search uses an APP_KEY-backed blind index. The current order detail exposes only authorized normalized data plus 25 immutable snapshot metadata entries; no raw provider body, token, cursor or queued payload is exported.

Authorization consumes state before exchange, with no DB locks over external I/O. The post-exchange transaction rechecks actor/session/permission, intent expiry/cancellation, exact redirect and provider-returned store identity under a store-specific advisory lock and merchant lock. Disconnect cancels all still-live intents for that merchant (including in-flight consumed intents) and advances connection generation. A late callback or refresh cannot resurrect disconnected credentials. Reauthorization of the same store retains its identity/history; ownership transfer remains unavailable.

Refresh claims a credential nonce/lease under current authority, releases locks during transport and compares nonce/version/generation/current authority before storing encrypted rotated credentials. Competing callers get a bounded busy result. An expired refresh lease is an unknown rotating-token outcome: invalidate local credentials and require reauthorization; do not replay a potentially consumed refresh token. Scope or identity changes fail closed. GuardedHttp has an empty verified-host allowlist by default, rejects HTTP/IP/userinfo/non443/unapproved/redirect destinations, uses verified TLS and bounded connect/request/read limits, bounds streamed JSON bytes/depth, and returns static classifications rather than upstream bodies. It is infrastructure for a future verified adapter, not an enabled Salla client. GET transient failures use durable bounded retries; token exchange/refresh POSTs never retry blindly.

## Synchronization, source changes and recovery

Each tick claims a 60-second durable lease, restores originating current authority and executes at most one page/row. HTTP fetches occur outside transactions. The following transaction rechecks merchant/user/session/token/role, connection generation and lease before committing orders, page receipt and next cursor atomically. Redis/Horizon is notification transport, not authoritative progress. ProcessStore jobs are encrypted and carry only merchant/work UUIDs on the existing bulk queue. `commerce:recover` republishes due unleased/expired work in batches of 100. Failed/unknown authorization never becomes successful work because a queue is retried.

Internal page caps are 50 orders/512KiB, 10 pages (500 records) per automatic segment and 1,000 records per run. A capped segment requires explicit, position-bound idempotent resumption; it cannot silently run an unbounded provider listing. Five attempts bound crash/transient recovery; Retry-After is respected and clamped to 1–900 seconds. Manual retry cannot bypass a future retry timestamp. Incremental checkpoint advances only after the complete page chain; opaque pagination cursors/checkpoints are encrypted and never accepted as arbitrary network URLs. Duplicate snapshots are no-ops, while repeat pages are a safe failure rather than an infinite loop. These are ClickToShip internal limits, not verified Salla pagination guarantees.

Source timestamps are not receipt order. Newer known source updates can become current; older/equal/undated conflicting observations remain immutable history. An unresolved conflict blocks new draft conversion even if the browser sends an acknowledgement. It requires a genuinely newer authoritative observation; no UI checkbox can manufacture source truth. Linked drafts always remain unchanged and carry a source-review warning. Existing draft editing/reconciliation stays in Shipping; no order cancellation calls a carrier or releases funds. Snapshot history metadata is available, but there is no arbitrary historical-PII export or automatic source-conflict adjudication.

## Draft preparation and experience

Single conversion requires explicit current snapshot/version, merchant-supplied origin/service/parcel review, canonical preview hash and request key. It additionally requires orders.read and shipments.write. Source amount/currency/COD cannot be overridden through review; unknown payment/fulfillment/COD, non-SAR currency, positive COD and unresolved source conflicts fail closed. Zero COD must be explicitly present in normalized source data. No weights, package dimensions, goods manufacture country, HS codes, carrier eligibility, taxes or exchange rates are invented.

Shipping.importDraft applies the existing parser/readiness/current actor fences; Catalog locking preserves service validation consistency. The draft/link/event/replay effect commits together under the merchant root. Retries by different actors or requests return the existing link; a crash cannot commit a draft without its link. No quote acceptance, carrier submission, wallet command, paid label, COD settlement, source fulfillment write-back or external customer notification exists in Commerce.

Batch preparation selects at most 25 distinct same-store orders, previews each, requires explicit confirmation, stores encrypted reviewed inputs and processes one order per transaction. Invalid rows produce durable partial errors; valid rows commit independently. A corrected retry/new batch cannot duplicate an existing draft. The initial review UI provides real entered origin/packages/service and optional recipient corrections; complete international declaration/item metadata is accepted through the typed API but missing international data requires the established Shipping/Customs workflow. No fabricated declaration defaults or simplified customs bypass.

Four bilingual merchant screens: store-integrations, store-orders, store-order and store-syncs; existing organization settings and searchable navigation link them. The platform adds a count-only platform-commerce section and the merchant dashboard shows only permitted local order/review/link counts. Synthetic stores are explicitly labeled and live Connect/Sync buttons are disabled. Service lists use the existing /rates authority; unavailable/no-config data is not simulated. Current order links preserve safe UUID context across locales, never tokens/codes/PII. Generation fences discard old merchant responses, review edits invalidate previews, and server expected-merchant guards remain mandatory. Charts/forms/tables reuse existing design primitives, RTL/LTR and responsive layouts; no dependency added.

## Webhook and operational policy gates

The external route is code-disabled before any provider parsing. No Salla signature header, event name, replay window or delivery retry/ACK contract is claimed. The interface must return a verified store/event identity only after official authenticity/replay checks. The synthetic test protocol is explicitly a different private fixture protocol. Tests prove invalid signature/replay/collision handling, not Salla compatibility.

Authenticated internal signal receipts deduplicate by scoped event identity and compare body digest; unknown signals quarantine metadata only. Uninstall revokes local authorization and fences late work. Sync signals may enqueue a reconciliation read under the persisted installer origin; current expiry/revocation can block it. No webhook creates or edits a shipment draft. Long-lived automated synchronization authority/consent, official event semantics and lawful retention/deletion rules require approval before real ingestion; historical encrypted records are not automatically deleted.

Platform commerce permission authorizes counts only, separated verified/synthetic store counts and current work/review/failure metadata. It cannot open store tokens/orders. No provider-specific private support grant route was invented; private support policy/permission may be added only with the existing exact independent grant discipline. Normal member access remains subject to ordinary merchant RBAC regardless of platform role. Real Salla setup and its staged verification checklist are in ../integrations/SALLA_EVIDENCE.md. All existing accounting, Aramex, customs, notification and production gates remain closed.
